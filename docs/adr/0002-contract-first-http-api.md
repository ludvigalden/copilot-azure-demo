# 0002 - Contract-first HTTP API

- **Status:** Accepted
- **Date:** 2026-10-01

## Context

The HTTP API has three independent consumers, written in three
languages: the C# server that implements it, the TypeScript client the
SPA calls it with, and the Power Platform custom connector definition
that exposes it to Power Platform. If each consumer is written by hand
against a reading of the others, the three drift apart silently, and every
change to the surface costs three coordinated hand edits.

## Decision

One OpenAPI 3.0.3 document, `contracts/openapi/openapi.yaml`, is the
single source of truth for the HTTP surface. Everything else is
generated from it and committed:

- The C# server's abstract controllers are generated at build time by
  NSwag; the hand-written controller is a small sealed subclass.
- The TypeScript client's types are generated by openapi-typescript;
  the SPA calls the API through openapi-fetch against those types.
- The custom connector definition is derived from the document by the
  Microsoft OpenAPI dev tool (`hidi`) in swagger 2.0 form, with a small
  `jq` step setting the connector's host expression.

One script, `contracts/openapi/generate.sh`, runs all three
generations, so there is exactly one way to regenerate. The generated
files are committed and never hand-edited; a diff on a generated file
always means the contract changed.

Continuous integration lints the document with Spectral, runs the
generation script, and then fails the build if `git diff` shows any
change or `git status` is not clean. An unregenerated contract edit
therefore turns the build red before it can be merged.

## Consequences

- The three consumers cannot disagree: they are three projections of
  one reviewed document.
- The drift gate is exact rather than advisory; it compares committed
  bytes against regenerated bytes.
- Generated files appear in diffs of contract changes. This is
  intentional: it makes the blast radius of an API change visible in
  review.
- The generation script needs the .NET SDK and npm dependencies, so
  it runs after the standard setup steps in CI and local development.
